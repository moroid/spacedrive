# SpacedriveフォークへのMDI・ワークスペース移植計画案

作成日: 2026-10-17。状態: 提案。今回行うのは調査と計画作成まで。フォーク作成・依存導入・実装・既存DBの移行は未実施。

## 1. 目標と推奨方針

Spacedriveのデザインを土台に、現在開発中のMDIとタスク単位のワークスペースを使えるWindowsファイラーを作る。「ワーク機能」は、現在のタスク作成・切替・複製・保存・復元・基準フォルダー・JSON入出力を指すものとして計画する。

**推奨は、Spacedriveを別リポジトリへフォークし、専用のワークスペース画面を追加する方式。** 現行アプリの色だけを変更する方式とは区別する。現行版は比較・復旧用に維持し、フォーク側で試作を評価してから主開発先を切り替える。

MDI配置・タスク保存・Windowsファイル操作は、現行実装を移植候補にする。Spacedriveの画面部品をそのまま複数配置するだけでは独立したMDIにならないため、一覧の表示とデータ取得を分離し、MDIごとの状態を明示する。

最初からSpacedriveの全機能をMDI化しない。まずローカル／UNCの通常フォルダーを対象に、現在の業務機能が成立する画面を完成させる。Spacedrive固有のライブラリー・分散インデックス・クラウド・メディア分析等は、ワークスペース移植の必須対象に含めない。ただし、元の機能や画面を調査前に一括削除することもしない。

## 2. 手元のソースから確認できたこと

調査対象: `spacedrive-main/spacedrive-main/`。ZIP展開物のため上流コミットSHAは未確認。以下はこの展開物の事実であり、上流最新版やビルド成功を保証するものではない。

| 項目 | Spacedriveの状態 | 移植への影響 |
| --- | --- | --- |
| 技術 | Tauri 2、React 19、Zustand 5。Bun workspaceとRust workspace | 主要技術は近いが、現在のnpm/Vite単一アプリから単純コピーできない |
| 外観 | `ShellLayout.tsx`、`TopBar`、`SpacesSidebar`、一覧・グリッド等 | 外枠、色、文字、メニュー、一覧の外観を土台にできる |
| UI依存 | `@spacedrive/tokens`、`@spacedrive/primitives`、Tailwind等 | 別配布パッケージもあり、取得可能性・ライセンス・バージョン固定を確認する必要がある |
| タブ | `TabManagerContext.tsx`にタブと表示設定、`sd-tabs-state`保存キー | 現行タスク保存との二重管理を避ける必要がある |
| ナビゲーション | router経由。`TabView.tsx`は共有routerを使う現状と将来の分離を記載 | 複数MDIに同じURL・履歴を共有させない設計が必要 |
| 選択・一覧状態 | `ShellLayout`配下に`SelectionProvider`・`ExplorerProvider` | 画面全体の状態とMDI内の状態を分割する必要がある |
| キー入力 | `useKeybind`が共通listenerとネイティブ登録を利用 | MDIごとに同じキーを重複登録しない |
| ツールバー | `TopBarPortal`や共通のレイアウト情報を利用 | 複数MDIのツールバーが同じ場所へ出力されないようにする |
| 一覧取得 | `@sd/ts-client`、`SdPath`、library query等に依存 | 見た目だけの差替えで現行ListingControllerへ接続できない |
| 配布 | Tauri設定に`sd-daemon`外部バイナリ、デーモンのビルド手順 | 現行の単体EXE同等の配布を最初から約束しない |
| 外枠 | 展開物のTauri設定は`decorations: true`、透明化等を指定 | Windowsフレームレスは現行要件に合わせて別途統合する |
| スクロール | 共通CSSにスクロールバーを隠すルール | 業務一覧・多段MDIでは到達性を優先して局所的に上書きする |

参照ファイル: `apps/tauri/package.json`、`apps/tauri/src-tauri/{Cargo.toml,tauri.conf.json}`、`apps/tauri/src/index.css`、`packages/interface/src/{ShellLayout.tsx,router.tsx}`、`components/TabManager/`、`routes/explorer/{context.tsx,ExplorerView.tsx,hooks/useExplorerFiles.ts}`。

## 3. 方式の比較と着手条件

| 方式 | 利点 | 負担・制限 | 判断 |
| --- | --- | --- | --- |
| Spacedrive全体をフォークして拡張 | 実際のデザイン・部品・周辺画面を利用できる | デーモン、依存、共有状態の分離が必要 | 推奨。小さい試作で成立を判定する |
| 現行アプリへ外観だけ移植 | 現行の保存・Windows操作を維持しやすい | デザイン再現に差が出る。Spacedrive自体のフォークではない | 試作が不成立の場合の代案。無断で切り替えない |
| 両方のアプリを別ウィンドウで連携 | 本体改造が少ない | 1画面内のMDIと統一操作にならない | 採用しない |

フォーク方式を進める前に、Windowsで未改造版を起動できることと、2 MDIの状態分離が成立することを確認する。成立しなければ、その原因と代案を提示して方式を決め直す。「CSS変更だけで移植完了」とはしない。

## 4. 画面とデザイン

- 外枠・サイドバー・メニュー・色・文字の階層・一覧の選択表現はSpacedriveを基準にする。採用する一覧／グリッドとテーマの実画面を先に記録し、比較画像で評価する。
- 上部は現行要件どおり32pxを基本に1段。アプリアイコン、ワーク選択、共通メニュー、移動余白、Windows標準キャプション記号を配置する。
- 左サイドバーはワーク、共通お気に入り、フォルダーツリー。SpacedriveのSpacesやLibraryを現在のタスクと同一概念にはしない。名称・データを分ける。
- 中央をMDI作業領域にする。MDIはタブ列、移動グリップ、戻る／進む／上へ、パス、一覧、短い状態行で構成する。子MDIはアプリ内のフレームレス領域とし、OSウィンドウを大量生成しない。
- 多段タブ、タブ名と閉じる操作の一体化、同名タブ識別、アクティブMDIだけの全周線を維持する。
- 囲み・余白・常設ボタンは現行のコンパクト要件を優先する。Spacedriveの大きい余白や角丸を各MDIに重ねない。右クリックメニューとキーボードで操作できるようにする。
- ファイルはWindows Shellアイコン、操作はFont Awesome、右上3操作はWindows標準記号という指定を維持する。SpacedriveのPhosphorアイコンは採用画面のアプリ内操作から段階的に置換する。
- 詳細インスペクターを残す場合は1つだけ置き、アクティブMDIの選択に追従させる。初期移植で新たな必須機能にはしない。

## 5. 状態とバックエンドの境界

```text
フォークの外枠・テーマ・サイドバー
  └ ワーク選択／WorkspaceStore（タスク保存の正本）
      └ MDI Canvas（既存の配置モデル・投影・D&Dを移植）
          └ PaneSessionごとに独立
              ├ タブ・パス・戻る進む・選択・検索・スクロール
              └ Spacedrive由来の一覧表示部品
                  └ ExplorerBackend境界
                      └ 現行Windows一覧／Shell操作／監視サービス
```

初期ワークスペース画面のファイル処理は現行Windowsバックエンドを接続する案を推奨する。Spacedrive固有のデータモデルへ全業務データを変換する作業を同時に行わない。元のSpacedrive画面は元のサービスを利用してよいが、同じワークスペース内の一覧を二つのエンジンで同時管理しない。

これは接続実装が不要という意味ではない。一覧部品から`@sd/ts-client`依存を切り離す範囲を試作で測り、表示専用部品への抽出が過大ならその時点で方式を再評価する。モック表示だけでは成立と判定しない。

状態の責任:

| 単位 | 持つもの |
| --- | --- |
| アプリ共通 | テーマ、共通お気に入り、ファイルジョブ、クリップボード、1つのキー入力ディスパッチャー |
| ワーク | MDI所属・配置・分割比率、各タブの保存状態、アクティブMDI、基準フォルダー |
| MDI／タブ | パス・履歴・選択・列・表示・検索・スクロール・要求世代。キーの対象はアクティブMDIのみ |
| 一時操作 | パス編集中の文字列、ドラッグ追従枠、スナップ候補、確認ダイアログ。保存しない |

グローバルURLはワークスペース画面の選択だけに用い、MDIのパス・履歴の正本にはしない。上流Providerを使う場合もMDI／タブの識別子を渡し、現在の共有routerへの同期を専用画面では分離する。タブIDを保ったままMDI間を移動し、履歴・選択・一覧セッションを意図せず初期化しない。

保存の正本は現行SQLiteのタスク形式を優先する。Spacedriveのタブ保存との双方向同期は作らない。初期は別アプリID・別データフォルダーを使い、現行DBを直接開かない。既存タスクJSONをコピーして読み込む経路から始め、将来DB移行を行う場合はバックアップ・版検査・失敗時復旧を別工程で検証する。

## 6. 段階的な実装

### Phase 0: フォーク元の固定と未改造版の起動

- 上流URL・コミットSHA・ZIPとの対応を確認する。GitHub上のフォークとローカル作業先を作り、upstreamと自分のoriginを区別する。実行は実装開始後。
- LICENSE・NOTICE・依存と外部アセットの台帳を作る。上流ロゴ・製品名・更新先・署名設定を自分の配布に引き継がない。
- Bun、Rust、Windows SDK、デーモン等の必要条件を固定する。展開物はRust 1.97.1を指定しているため、利用可能性も確認する。
- Windowsで未改造のTauri版をビルド・起動し、好みのデザインと一致する一覧・グリッド・テーマを記録する。未改造版が起動できない場合は先に原因を切り分ける。

完了条件: 出自・依存・手順が記録され、Windowsで基準画面が表示できる。

### Phase 1: 2 MDIの実証試作（移行可否の判定点）

- 専用ワークスペース画面を追加し、左右に独立した2つのMDIを表示する。
- 現行の通常フォルダー一覧を境界経由で表示し、Spacedrive由来の外観・選択表現を使う。
- A/Bの異なるパス・タブ・選択・履歴を保持する。片側の移動・Ctrl+A・F5・戻るが他方へ作用しないことを確認する。
- 共通TopBar・portal・キー登録・Providerの共有による衝突を解消する。

完了条件: 実ファイル一覧が2 MDIで独立し、Spacedriveの見た目を保つ。残す上流画面が壊れていない。ここで依存分離の工数と残る問題を再見積もりし、本移植へ進むか判断する。

### Phase 2: MDI配置とタブ操作

- 既存の配置モデル、寸法投影、最大化／復元、自由配置、サイズ変更を移植する。
- 多段タブ、MDI間タブ移動、分離・統合、追従枠、四方向ガイド、端・隅スナップを接続する。
- 確定前は保存モデルを変更せず、Esc・capture喪失・blur・ワーク置換で取消する。
- 過密時の最小寸法、スクロール座標、安定した計測ホストを移植し、震えを再発させない。

完了条件: 07計画のBUG-1/2/4/5/6、UI-10に対応した結果とプレビューが一致する。

### Phase 3: ワークの保存・切替・既存データ

- 作成・名前変更・複製・並べ替え・削除、基準フォルダー、JSON入出力を接続する。
- 約1秒の自動保存、手動保存、保存成功後のワーク切替、閉鎖タブ復元を移植する。
- 同じワークを二つの保存系が上書きしないこと、ワーク切替後に遅い一覧応答が混入しないことを検証する。

完了条件: 再起動・JSON往復後もMDI所属・配置・タブ状態が一致し、旧データを壊さない。

### Phase 4: Windows操作と仕上げ

- コピー・移動・名前変更・削除・フォルダー作成・既定アプリ起動、確認・競合・取消・ジョブ履歴を接続する。
- MDI間ファイルD&D、クリップボード、共有監視、検索・列設定を移植する。ファイルD&Dとタブ／MDI移動を明確に分離する。
- Shellアイコン、Font Awesome、標準キャプション、フレームレスの子画面、パス直接編集・祖先ダブルクリック・欄外取消・補助マウス履歴を統合する。

完了条件: 現行の業務操作と保護処理を退行させず、デザインと操作の一貫性がある。

### Phase 5: 回帰検証・ポータブル配布・切替

- 型検査、移植したドメイン試験、DOM操作試験、Rust試験、Windowsネイティブ試験を行う。上流の既存チェックも採用範囲で維持する。
- 一覧・詳細・アイコン、10万件の仮想表示、6 MDI、多段タブ、狭幅、両テーマ、実DPIとDPRを区別して比較する。
- フレームレス・ヒットテスト・最大化・Snap、実IME、物理補助マウスを確認する。利用できないモニター・SMB等は未検証として記録し、現行の未確認を移植で解消済みにしない。
- EXEと必要なデーモン・資源を洗い出し、EXE隣のdataへ集約する。デーモンを残す場合は子プロセスの起動・終了・多重起動・保存先・ポート競合・終了後のフォルダー移動も確認する。
- ZIPにユーザーデータを入れず、必要ファイルの許可リスト、バージョン、ハッシュ、展開後の起動を検証する。現行の6ファイル構成を新構成へそのまま適用しない。

完了条件: 比較検証と残る条件を提示し、新版ZIPから復元・業務操作・終了・持ち運びが成立する。現行版から主開発先を切り替えるのはこの判定後。

## 7. Gitと変更管理

- 上流フォークと現行アプリは別リポジトリ。展開済みソースを現行リポジトリへ丸ごと追加しない。
- 現行の移植元コミットSHAと、採用したファイル・変更理由・帰属を記録する。
- 「起動基準」「2 MDI分離」「配置」「ワーク保存」「Windows操作」「配布」の単位でコミットし、各時点を起動可能に保つ。
- 上流更新は独立した変更として取り込み、ワークスペースの回帰を確認する。上流の全ファイルへ広範な修正を入れるより、専用画面と境界へ変更を寄せる。

## 8. この計画の判断事項

推奨案は「Spacedriveの実際のフォーク＋専用ワークスペース画面＋現行Windowsサービスの移植」。最初の到達点はPhase 1の2 MDI試作とする。全移植の工数は、未改造版のWindowsビルドと一覧部品の分離を試す前には確定しない。

今回の計画を承認して実装へ進む場合も、最初から現行版を置き換えず、Phase 0〜1の結果で継続可否を判定する。フォーク先アカウント／リポジトリ名と、見た目の基準にする画面は着手時に確定する。
